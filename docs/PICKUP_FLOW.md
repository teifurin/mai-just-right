# 有界真实到店自取流程

本次新增独立网页真实流程：搜索门店 → 读取经过核对的门店菜单子集和适用优惠 → 输入数量、预算和是否允许额外餐品 → 构造相同需求单点基准与组合候选 → 对每个购物车进行官方核价 → 显示范围内建议与计算依据。

**2026-10-20 已在本机生产 Worker 上完成有限范围的真实网页端到端验收。** 所测范围为一个门店、麦辣鸡腿汉堡、中薯条、明确中杯可乐，以及同规格三件套；覆盖不允许额外餐品、允许额外餐品和预算不足分支。另以 360 像素手机尺寸触摸模拟完成选店至推荐。它不代表任意门店、全菜单、所有账户或物理手机均已验收。私有映射与 Token 不入库；未配置映射时返回 `PROFILE_REQUIRED`，不会回退到演示价格。

## 第一个范围

- 一个明确选定的门店和到店自取渠道，不支持跨店或配送比较。
- 最多 8 种标准化需求餐品、16 个组合、总共 12 份食物。每个组合最多使用一次。
- 用户勾选要比较的组合，所有满足需求的组合子集补齐相同的单品需求；超过 5 个候选立即要求缩小选择，不以列表展示价筛选。
- 一个单点基准与最多 5 个候选全部顺序官方核价后，才按真实应付总额排名。缺少任何必要查询或应付金额，整次流程失败。
- 查询并展示所选门店的适用优惠；**第一范围不自动使用或叠加账户券，不执行领券**。看见优惠不代表候选已享受该优惠。
- 套餐组成与规格映射须由操作者通过当前详情逐项核对，不从标题推断；覆盖不匹配时不要把该组合加入映射。
- 只表述“本次已选范围内”，不宣称整店、全账户或全局最低价。

## 运行时映射配置

在可信服务端环境设置 `MCD_PICKUP_PROFILE_JSON`。它是私有运行配置，不放入前端、Git、公开文档、截图或本地历史。它不包含 Token，凭证仍单独由 `MCD_MCP_TOKEN` 提供。现有所有者访问控制保持不变；身份校验在读取映射之前执行。

配置必须由操作者从当前认证 `tools/list` 和真实门店、菜单、套餐详情、适用优惠以及核价响应建立。没有这些材料不要填写。仓库的 `tests/pickup.test.mjs` 只描述**完全合成、不可连接官方的格式示例**，不得将其中字段或编码当作官方定义。

配置字段：

| 字段 | 约束 |
| --- | --- |
| `version`, `reviewed` | `1` 和 `true`，表示操作者已逐字段核对 |
| `pickupValue` | 当前 Schema 确认的到店自取渠道值；不是推断默认值 |
| `schemas` | 按工具名保存完整 `inputSchema`；每次流程和每次业务调用都与当前发现结果比较，变化即停止 |
| `stores` | 搜索参数模板、渠道路径、结果数组 `rowsPath`、编码 `idPath` 和名称 `namePath` |
| `menu`, `coupons` | 参数模板、门店 `storePath` 与渠道 `channelPath`；优惠另需列表和名称路径；菜单可指定 `storeNamePath` |
| `details` | 可选，最多16个明确范围的 `query-meal-detail` 参数模板，逐个重新读取 |
| `products` | 1–8个单品映射，每个对应一种需求餐品 |
| `offers` | 最多16个组合映射，每个另有 `coverage`，列出经过详情核对的餐品与数量 |
| `quote` | 固定门店/渠道参数模板、`itemsPath`、官方应付总额 `totalPath` 与明确的 `fen` 或 `yuan` 单位 |

参数模板中的 `{ "$context": "storeId" }`、`{ "$context": "channel" }`、`{ "$context": "search" }` 是本项目模板指令，不是官方字段。参数对象的其他字段名和值必须来自实际 Schema。门店搜索绑定渠道；菜单、优惠、详情和核价同时绑定同一门店与渠道。

搜索中的城市也受服务端映射限制；输入框只向该映射提供关键词，不保证任意城市可用。本次私有映射只验证既定城市。实际菜单的主商品和详情子项不能混用：可乐需用菜单主商品编码并在 `roundList` 明确中杯，不能省略规格，也不能把中杯子项编码直接作为单点主商品。`namePath` 可指向已选择规格的真实名称，以便页面显示明确杯型。

单品/组合映射包含本项目 `id`、数据来源 `source`（`menu` 或 `detail0` 等）、`rowPath`、`namePath`、`codePath`、`expectedCode`、`quoteItem`、`quoteCodePath` 与 `quantityPath`。每次读取的新行必须仍有经过核对的 `expectedCode`；菜单重排或编码变更立即报错，不静默把别的商品当成原商品。`quoteItem` 中 `{ "$row": ["已核对的字段路径"] }` 取自本次真实响应；套餐规格等复杂结构亦必须来自真实详情而不是编造。`quoteCodePath` 指向核价中的主商品编码，必须与本次真实行的已核对编码一致。`quantityPath` 指向核价单品数量字段。每个套餐还必须有非空 `assertions`（source、path、expected），覆盖实际组成、规格选项与数量；这些字段变化时旧覆盖声明立即失效。有子项规格时以 `quoteBindings`（quotePath、source、sourcePath）核对生成的核价子项与当前详情一致。这些断言仍需要操作者完整审核，程序不能证明人工覆盖映射的语义正确。

路径仅允许自有属性、不接受原型相关字段。完整 Schema 逐结构比对，不依据工具名称猜测兼容。保留的所有查询均为原只读允许列表内工具。

## HTTP 接口

均为经过现有所有者鉴权的 `POST /api/mcp`：

- `action: "pickup-stores", search`：返回最多50个真实搜索结果。
- `action: "pickup-catalog", storeId`：重新读取菜单、优惠和可选详情，返回已核对子集，**不返回私有映射或核价参数**。
- `action: "pickup-recommend", storeId, demand, budgetCents, allowExtras, offerIds?`：再次实时查询目录，验证范围，构造并核价全部候选。预算为非负整数分，需求数量合计不超过12。`offerIds` 为明确选定组合；空数组表示仅比较单点，不会偷偷加入套餐。

成功结果含 `source: live`、门店、渠道、需求、基准、候选、`best`、预算状态、核价时间、范围和限制。所有额外餐品由实际覆盖数量减去原需求计算，不接受调用者自报“额外0份”。金额不足预算时明确 `withinBudget: false`。没有候选不构造伪优惠。

真实结果仅在当前页面内存展示，不混入演示历史。中断或改变选择后旧核价不可继续作为新需求的结果。

本次真实验证结果见 [网页证据](evidence/pickup-browser-2026-10-20.json)与[触摸模拟证据](evidence/pickup-mobile-2026-10-20.json)。响应未被 mock，实际连接官方 MCP；真实账户数据未写入 localStorage。生产运行时的重定向兼容问题已修复，并有拒绝重定向的安全回归。

当前账户在所测门店的适用券列表为空，因此尚未真实验证有券名称映射、券叠加、其他门店、其他餐品或物理手机。私有映射对尚未核对的券名路径保持拒绝，出现非空券列表时须先核对真实结构。限流、超时、会话失效、权限错误等异常主要由合成协议测试覆盖，不通过主动制造真实限流来验证。
